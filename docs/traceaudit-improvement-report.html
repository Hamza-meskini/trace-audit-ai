Summary

TraceAudit's core design is sound: Python, not the model, decides each verdict over an explicit logic tree, and an offline replay reproduces all 240 saved verdicts. Nova scores 88.3% (SD 2.4) over 5 runs of 48 requirements. Treat that as a development-set figure: Nova is saturated, and it measures the batch path with Maverick contracts, while production runs the single path with GLM contracts sent to TokenRouter.

The largest measured gain is committed but not merged. Two deterministic fixes take the replay from 212 to 231 of 240 and CONFLICT recall from 32/50 to 50/50, with 0 broken rows and 0 unsafe auto-closes. Shipping them safely needs three things: a replay expectations ledger, a verdict-logic cache key and review-state preservation (ACC-01, TRU-01). Further offline levers reach 234/240. Source association plus Python gate signals raise correct auto-closes from 12 to 39 of 100, with 0 wrong.

The 0-unsafe record holds on the benchmark only. Four trust gaps remain: a probe shows a PROVEN condition whose quote contradicts the observed value ending SUPPORTED; citations can be re-pointed to uncited evidence; a pre-v3 run wrongly auto-closed CHG-003 on another requirement's rows; and the VALID write at verdict_aggregator.py:556 erases warning markers. The review record also overstates human review and loses sign-offs on re-audit.

Failure handling is the weakest area. In today's outage every model call returned HTTP 400. Each became None and the run went on for about 27 calls; profiling fell to 75% role accuracy and discovery failed with a misleading error. The deployed app would instead persist rule-engine verdicts at 92-95 confidence, delete evidence links and findings, cache the result and keep regex-only requirements. The first fixes are typed errors, failing closed and never persisting fallback output (REL-01, REL-02).

The owner needs to decide on five points: third-party egress (TokenRouter, Google embeddings, vision fallbacks), rotating the Gemini key that main still sends in URLs, keeping originals only on local disk, deletion that removes database rows only, and an unused visitor-data API. Measurement order: the ledger and CI gate now; raw recording, run validity and the production path next; baseline runs when the endpoint returns; then the hard benchmark. Majority voting is not worth it: 42.9 vs 42.4 of 48 at 3x the cost.

How this was made

Seven specialists each took one area of the platform. They read the code, the end-to-end review written earlier today (docs/review-2026-11-08.md) and today's measured reports. The areas were verification accuracy; document understanding; reliability, operations and cost; trust and the review workflow; evaluation; security and deployment; architecture and product UX. Review item numbers such as C1 or H3 refer to that document.

Each area's proposals went to an independent verifier, who re-checked every claim in the code and the git history. Of 83 proposals, 52 were confirmed in full and 31 in part; the parts that failed are listed under Checked and dropped. A final pass merged duplicates into 66 improvements and ranked them. No separate completeness pass ran, so the areas nobody examined are named under Decisions for you. Before publishing, the cited lines of the ten top priorities were re-read: nine matched, and one claim about the Excel export (TRU-02) was corrected.

Accuracy deltas come from the offline replay harness (evaluation/replay_verification.py). It is exact for aggregation, qualification and review-gate changes. It cannot measure prompt, schema or model changes, which need repeated live runs under evaluation/ACCURACY_PROTOCOL.md.
